# Repository architecture

> **Factual reference.** This file describes the current state of the repository. Update it when the repository changes. The code is the source of truth. If this document and the code disagree, the code wins.

## Layout

| Path                 | Contents                                                                                                                           |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| `backend/`           | Go HTTP backend service for scrubbing, request handling, configuration, and private storage. The service has its own `AGENTS.md`.  |
| `frontend/`          | TypeScript and React frontend service on TanStack Start and Vite. `pnpm` manages the service. The service has its own `AGENTS.md`. |
| `docs/`              | Cross-service documentation. General guides are under `docs/agent/`. Factual references include this file.                         |
| `docker-compose.yml` | Runs the backend and frontend together for local development.                                                                      |

## Service integration

- Clients send public application requests to the frontend. Frontend server code calls the backend over HTTP.
- The frontend validates the backend URL and creates request-scoped Ky clients with this URL as the base URL.
- On Vercel, `vercel.json` supplies the backend URL through a service binding to the backend container. For local development, `docker-compose` or the shell supplies the value.
- The first three `vercel.json` rewrites proxy `/relay/static/*` and `/relay/array/*` to US Cloud PostHog assets. They proxy other `/relay/*` requests to US Cloud PostHog ingestion. These rewrites run before the frontend catch-all.
- The browser tRPC client reads the current PostHog IDs for each request after the SDK initializes. It sends `X-POSTHOG-DISTINCT-ID` and `X-POSTHOG-SESSION-ID`. An uninitialized SDK sends neither header. The frontend server forwards these incoming headers unchanged on workflow calls only. The backend validates them and uses them for server events. Health calls do not forward them.
- See [backend telemetry](../backend/docs/architecture.md#posthog-telemetry) and [browser analytics](../frontend/docs/architecture.md#browser-analytics) for service details.
- The root tRPC router registers only `wizard` ([`routers.mod.server.ts`](../frontend/src/shared/libs/trpc/routers/routers.mod.server.ts)).
- The backend provides `GET /api/health` ([`backend/main.go`](../backend/main.go)). The shared frontend health-check Ky client remains, but no frontend tRPC procedure calls backend health ([`http-client.mod.server.ts`](../frontend/src/shared/libs/ky/http-client.mod.server.ts)).
- The wizard tRPC router provides typed proxies for workflow configuration, upload grants, dry-run inspection, revision-bound scrubbing, download-grant refresh, and confirmed deletion.
- The tRPC workflow sends only small JSON values. It does not send file bytes.
- The Go backend owns the maximum source size. The frontend reads it at runtime through `getWorkflowConfig`.
- The scrub workflow accepts PDF input only. The backend checks for `%PDF-` at offset zero and then parses the PDF structure.
- The browser uploads the PDF directly to private R2 with a presigned PUT URL. No frontend route accepts file bytes.
- The home route mounts `FileWorkflow`. After upload, it runs one `wizard.dryRun` mutation and displays the backend metadata inventory as text. It keeps the reviewed key and ETag in memory ([`index.tsx`](../frontend/src/routes/index.tsx), [`file-workflow.mod.tsx`](../frontend/src/domains/wizard/components/file-workflow/file-workflow.mod.tsx), [`file-workflow-screens.mod.tsx`](../frontend/src/domains/wizard/components/file-workflow/file-workflow-screens.mod.tsx)).
- The user selects `Scrub it` to scrub the exact reviewed pair. A guard blocks duplicate clicks while the synchronous request is pending. A failure keeps the review and offers an explicit retry of the same pair ([`file-workflow.mod.tsx`](../frontend/src/domains/wizard/components/file-workflow/file-workflow.mod.tsx)).
- After scrub success, the result requests a fresh grant through `POST /api/files/download-grant` with the exact reviewed `{ storageKey, etag }` pair. The initial scrub response has no `expiresAt`. The result uses refreshed authoritative expiry, not an estimate from the initial link's approximate lifetime. The pair and grant stay in memory; refresh does not scrub again ([`file-workflow-download.mod.ts`](../frontend/src/domains/wizard/components/file-workflow/file-workflow-download.mod.ts), [`wizard-router.mod.server.ts`](../frontend/src/domains/wizard/wizard-router.mod.server.ts)).
- Download stays disabled on result entry until a valid grant arrives. The result checks expiry on return to the visible page and when Download is selected. It blocks expired navigation and refreshes one-shot. Missing output or refresh failure leaves no usable link and offers `Refresh download link`. Hiding the tab cancels scheduled renewal but keeps the expiry timer. The timer only disables the link at expiry while the tab is hidden ([`file-workflow-download.mod.ts`](../frontend/src/domains/wizard/components/file-workflow/file-workflow-download.mod.ts), [`file-workflow-screens.mod.tsx`](../frontend/src/domains/wizard/components/file-workflow/file-workflow-screens.mod.tsx)).
- While the result's download component is mounted and the tab is visible, it schedules renewal 2 minutes, or 120 000 ms, before the grant's authoritative `expiresAt`. It renews immediately if the grant is already within this lead time. Each new expiry sets the next schedule. A guard permits one scheduled renewal for each expiry value. Each refresh is a one-shot POST with no browser or transport retry. Download stays disabled while renewal is pending. Renewal does not poll processing ([`file-workflow-download.mod.ts`](../frontend/src/domains/wizard/components/file-workflow/file-workflow-download.mod.ts), [`wizard-router.mod.server.ts`](../frontend/src/domains/wizard/wizard-router.mod.server.ts), [`workflow-http-client.mod.server.ts`](../frontend/src/shared/libs/ky/workflow-http-client.mod.server.ts)).
- Leaving the result view, selecting `Start again`, or confirming deletion unmounts the download component. This cancels its schedule and expiry timer and removes its return listeners. Requests already sent can still finish. The hook ignores late refresh successes and failures after unmount ([`file-workflow-download.mod.ts`](../frontend/src/domains/wizard/components/file-workflow/file-workflow-download.mod.ts), [`file-workflow.mod.tsx`](../frontend/src/domains/wizard/components/file-workflow/file-workflow.mod.tsx), [`file-workflow-screens.mod.tsx`](../frontend/src/domains/wizard/components/file-workflow/file-workflow-screens.mod.tsx)).
- A ready grant supplies a native `Download PDF` link to private R2. The link uses `referrerPolicy="no-referrer"` and has no `download` attribute. The home flow offers `Start again`, download-link recovery, and `Delete files` on the result view ([`file-workflow-screens.mod.tsx`](../frontend/src/domains/wizard/components/file-workflow/file-workflow-screens.mod.tsx), [`file-workflow.mod.tsx`](../frontend/src/domains/wizard/components/file-workflow/file-workflow.mod.tsx)).
- `Delete files` opens a confirmation dialog. `Cancel` or Escape closes it without a delete request. `Confirm deletion` sends one `wizard.confirmDelete` mutation with `{ storageKey }` to `POST /api/files/delete`. A guard blocks duplicate confirmation. Download and the delete button stay disabled while the request is pending ([`file-workflow-deletion.mod.tsx`](../frontend/src/domains/wizard/components/file-workflow/file-workflow-deletion.mod.tsx), [`file-workflow-screens.mod.tsx`](../frontend/src/domains/wizard/components/file-workflow/file-workflow-screens.mod.tsx), [`wizard-router.mod.server.ts`](../frontend/src/domains/wizard/wizard-router.mod.server.ts)).
- Success shows `Deletion confirmed` and `No stored files remained when the backend checked.` It removes the usable download grant and link-recovery controls. Late refresh responses cannot restore Download. Failure shows `Could not confirm deletion. Files may remain. Try again.` It offers `Retry deletion` with another confirmation and requests a fresh download grant. Failure does not claim removal or guarantee that Download remains available ([`file-workflow-deletion.mod.tsx`](../frontend/src/domains/wizard/components/file-workflow/file-workflow-deletion.mod.tsx), [`file-workflow-screens.mod.tsx`](../frontend/src/domains/wizard/components/file-workflow/file-workflow-screens.mod.tsx), [`file-workflow-download.mod.ts`](../frontend/src/domains/wizard/components/file-workflow/file-workflow-download.mod.ts)).
- Source objects are private. The frontend passes logical `uploads/<fileId>` keys. The backend stores sources at `source/<fileId>` and results at `sanitized/<fileId>/<encodedETag>`. It encodes the source ETag with unpadded base64url ([`handler.go`](../backend/internal/handler/handler.go), [`storage_validation.go`](../backend/internal/storage/storage_validation.go)). Review and scrub use the same canonical source ETag. The backend reuses an existing result for that revision ([`file_workflow.go`](../backend/internal/handler/file_workflow.go)).
- The initial scrub grant and refreshed download grants contain direct private R2 GET URLs for the exact sanitized revision. These URLs request `Content-Disposition: attachment; filename="sanitized.pdf"`.
- The backend confirms full-flow deletion before it reports success. The operation removes the source and every sanitized revision for the file. It checks source absence with HEAD and result-prefix absence with LIST. Already-missing files count as success. Remaining objects or a dependency failure prevent success. Confirmed deletion shows absence at the time of the checks. The checks do not hold an atomic publication lock. A scrub that is already in progress can still write a cleaned file after that ([`delete_flow.go`](../backend/internal/handler/delete_flow.go), [`r2_delete_flow.go`](../backend/internal/storage/r2_delete_flow.go), [`file_workflow.go`](../backend/internal/handler/file_workflow.go)).
- Grant renewal does not extend object retention or confirm deletion. Grant expiry disables the download link; it does not confirm file deletion. The review separately warns that lifecycle cleanup can take longer than 24 hours after file expiry. This is not a guaranteed deletion deadline ([`download_grant.go`](../backend/internal/handler/download_grant.go), [`file-workflow-download.mod.ts`](../frontend/src/domains/wizard/components/file-workflow/file-workflow-download.mod.ts), [`file-workflow-screens.mod.tsx`](../frontend/src/domains/wizard/components/file-workflow/file-workflow-screens.mod.tsx)).
- Backend workflow errors contain safe public text. The frontend maps them to safe tRPC errors and does not return provider details.
